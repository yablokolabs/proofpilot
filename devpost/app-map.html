ProofPilot AI: App Map

A snapshot of the code at commit 08a388b. The code can change after this map was made.

What the app does

You paste text and select Check claims. The app finds the factual claims, searches the web for evidence, and marks each claim in your text as Supported, Contradicted, or Unverified. A click on a claim shows its evidence.

There are three main pieces: the page in the browser, one server route that runs the pipeline, and the checks in plain code that confirm the model's work.

One action through the code

A route to follow (reference route, not toured)

  1. The click. src/app/page.tsx, function check. It posts the text to /api/check and applies each event to the report state with applyEvent from src/lib/report.ts.
  2. The pipeline. src/lib/pipeline.ts, function runCheck. It extracts claims, locates them with locateClaims (src/lib/spans.ts), then retrieves and judges each claim, four at a time.
  3. The integrity check. src/lib/citations.ts, function validateVerdict. It keeps a citation only if its excerpt is in the retrieved page text, and it decides when a status becomes Unverified.

The route handler that connects the first two stops is the POST function in src/app/api/check/route.ts.

What counts as a claim, or how strict a verdict is
  • The SYSTEM text in src/lib/extract.ts and in src/lib/judge.ts.
  • The status rules in validateVerdict, src/lib/citations.ts. Its tests are in tests/citations.test.ts.
The limits
  • MAX_INPUT_CHARS and MAX_CLAIMS in src/lib/limits.ts.
The model or the search
  • DEFAULT_MODEL in src/lib/llm.ts, or the NEBIUS_MODEL variable in .env.
  • The search options in src/lib/retrieve.ts.
The status wording and the counts
  • summarise in src/lib/summary.ts for the logic, and HEADLINE in src/components/ReadinessSummary.tsx for the text.
Colours and highlight styles
  • The --color-* values and the .claim-* rules in src/app/globals.css.

A practice to reuse

Write down the thing that can fail, with the check that will show it.

The spec recorded one unknown before any code: the result for a claim comes from live search and a model, so it cannot be guaranteed (devpost/spec.md, "Decisions and Open Issues"). The agreed check was to run the same text several times and record the real results.

That check found a real defect. One claim received three different verdicts in three runs. The cause was that the model selected one side when the sources disagreed. The fix is a rule in code, with tests, not a change to a prompt only: validateVerdict gives Unverified when confirmed reputable sources have opposite stances (tests/citations.test.ts). After the change, the same claim was Unverified in three of three runs. The record is in devpost/checklist.md, "Revisions".

On another project: name the one result that you cannot guarantee, agree on a repeatable check for it before you build, and put the rule that protects it in code that a test can exercise.
